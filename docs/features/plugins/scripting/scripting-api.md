# F-EXT-002 — Скриптинг и автоматизация — API для своих операций над проектом

## Суть

Монтажёру нужно сделать над проектом одно и то же сорок раз: переименовать
и перепривязать сорок исходников, разложить монтаж по таблице (кто говорит,
с какой секунды, каким планом), отрендерить по куску на каждую метку с
именем метки в имени файла, поменять один параметр эффекта у всех клипов
дорожки, выгрузить в CSV список «клип — исходник — таймкод» для заказчика,
забрать материал из системы хранения. Руками это часы одинаковых движений,
и вопрос «а как это сделать программой» встаёт раньше, чем вопрос про любую
творческую функцию. Ответ у пяти редакторов устроен ЧЕТЫРЬМЯ разными
способами, и разница между ними — не язык, а то, ЧТО именно программа
трогает: живое приложение, файл проекта или отдельный параметр.

## У кого и как

Четыре модели, к которым сводится всё поле:

1. **Интерпретатор внутри редактора** (Vegas): скрипт — это команда
   редактора, живущая в его процессе и его меню.
2. **RPC к живому приложению** (Resolve, Premiere): внешний процесс
   разговаривает с запущенной программой через объектную модель.
3. **Обмен через формат** (FCP): API нет вовсе, автоматизация — это чтение
   и запись файла обмена сторонними программами.
4. **Скриптинг внутри параметра** (AE): выражение живёт в самом свойстве и
   считается на каждом кадре рендера, а не «один раз по нажатию».

| Редактор | Версия | Как называется | Как устроено |
|---|---|---|---|
| VEGAS Pro | 2026.0 | Scripting (.NET) + Application Extensions | скрипт — исходник `.cs`/`.vb` в папке `Script Menu`, компилируется .NET при запуске; попадает в меню Tools → Scripting, на панель инструментов и на горячую клавишу через те же диалоги Customize, что и родные команды. Расширение — скомпилированный DLL: грузится со стартом, живёт всё время работы, реагирует на изменения проекта, управляет воспроизведением, показывает немодальное окно. Командная строка: `/RUNSCRIPT`, `/SCRIPTARGS`, `/CMDMODULE` |
| Adobe Premiere | 26.x | UXP-плагины (с 25.6), CEP-панели + ExtendScript, C++ SDK | три параллельные платформы. CEP — «classic extensions… automate in-app workflows with ECMAScript 3»; UXP — ES2015, асинхронный DOM, панели и команды, распространение через Creative Cloud Marketplace (пакет `.ccx`, профиль издателя, требования DSA для ЕС). Правки идут транзакцией: `project.lockedAccess` → `executeTransaction(compoundAction)` — пачка действий отменяется одним Ctrl+Z |
| DaVinci Resolve | 21 (проверялось по README 20.x) | Scripting API | внешний Python 3 / Lua 5.1 подключается к `fusionscript.so/.dll`; «DaVinci Resolve needs to be running for a script to be invoked», но есть `-nogui`. Доступ настраивается в Preferences: только консоль / консоль и командная строка / **из локальной сети**. Меню Workspace → Scripts собирается сканом каталогов при старте |
| Final Cut Pro | 12.3 | своего API нет; FCPXML + Workflow Extensions | обмен — XML-документ (с 1.10 — бандл `.fcpxmld` с `Info.fcpxml` внутри), экспорт даёт выбор только «Current» или «Previous». Workflow Extension — отдельное приложение macOS, показанное панелью внутри FCP; в проект оно всё равно ходит через FCPXML |

## Фишка фишки

**1. У Vegas скрипт не «зовётся через API» — он СТАНОВИТСЯ командой
редактора, и поэтому экосистема чинит редактор за вендора.** Скрипт лежит
в `Script Menu` исходником, компилируется при запуске, а рядом кладётся
PNG 16×16 с именем `HelloWorld.cs.png` — и в меню появляется пункт со своей
иконкой, который дальше вешается на кнопку панели и на горячую клавишу теми
же диалогами Customize Toolbar / Customize Keyboard, что и родные команды.
Отличить свою команду от штатной пользователь не может. Обратная сторона
той же медали: раз скрипт — это исходник, который компилируется у
пользователя, то API редактора становится ПУБЛИЧНЫМ КОНТРАКТОМ. В 2026 году
из объектной модели пропал `Stereo3DOutputMode`, и штатный, поставляемый с
Vegas скрипт Batch Render Timer перестал компилироваться прямо в диалоге
запуска, с ошибками C#-компилятора и номерами строк. Готовая правка `.cs`
лежала в ПЕРВОМ же сообщении треда (02.04.2026), а вендор закрыл дефект
только в build 143 — отметка «fixed in b143» появилась 20.06.2026, через
два с половиной месяца. Ровно та же механика продлевает жизнь редактору:
Happy Otter Scripts даёт рендер через NVENC в Vegas 22 и старше на ЛЮБОЙ
версии драйвера Nvidia, а сторонний TTS-скрипт подключает синтез речи
там, где подписка Vegas 2026 даёт «всего» девять языков.

**2. У Resolve API — закрытый белый список, и он про КРАСКУ, а не про
монтаж.** Собрать монтаж с нуля можно: `CreateTimelineFromClips` и
`AppendToTimeline` принимают словарь `{mediaPoolItem, startFrame, endFrame,
trackIndex, recordFrame}` — то есть положить клип в нужную секунду нужной
дорожки. А вот ПРАВИТЬ собранное нечем: у `TimelineItem` есть `GetStart`,
`GetEnd`, `GetLeftOffset`, `GetRightOffset` — и ни одного парного сеттера.
Ни сдвига, ни трима, ни разреза, ни единого метода про переходы.
`SetProperty` принимает фиксированный список из трёх десятков ключей —
`Pan`, `Tilt`, `ZoomX`, `CropLeft`, `CompositeMode`, `Opacity`,
`RetimeProcess` — то есть встроенный трансформ и ничего кроме: параметр
произвольного OFX/ResolveFX-плагина не адресуется вообще. Зато в API есть
канал, которого нет в интерфейсе: у каждой метки лежит `customData`, и
документация про него честно пишет «not exposed via UI and is useful for
scripting developer to attach any user specific data». Скрипт может носить
в проекте свои данные, невидимые пользователю, — но только строкой и
только на метке.

**3. Одна цель, две противоположные цены: транзакция в процессе против
бандла на диске.** Premiere пришёл к тому, что скрипт обязан менять проект
ТРАНЗАКЦИЕЙ: `project.lockedAccess(() => project.executeTransaction(...))`,
и вся пачка правок становится ОДНИМ шагом истории. До этого было хуже, чем
«много шагов»: правки ExtendScript в панель History не попадали вообще, то
есть работу скрипта нечем было откатить, а собрать пачку в один Ctrl+Z, по
формулировке самой Adobe, «is impossible in CEP».
Цена — платформа: CEP и UXP не смешиваются («there is no way to have a
CEP/UXP hybrid»), у каждого члена API проставлена MIN VERSION, а сама
объектная модель до сих пор догоняет ExtendScript. FCP заплатил
противоположную цену: процесса нет вовсе, есть документ, и Apple сама
пишет про него — FCPXML «describes certain, but not all, aspects of
projects and events useful for other applications. But, it's not a
substitute for a native Final Cut Pro project». Что в файл не попало, того
для автоматизации не существует: включённость роли (Video/Audio/Caption)
FCPXML не записывает вовсе — заявка в Apple Feedback от 2023 г. на
2026-09-07 всё ещё открыта, и никакой сторонний инструмент про состояние
роли не узнает. Зато автоматизировать FCP можно на чём угодно и без строчки
API — вокруг формата выросли SwiftFCPXML, OpenFCPXMLKit, FCPBridge,
CommandPost, — и вендору не приходится держать совместимость ни с одним
интерпретатором.

## Плюсы

- Скрипт, ставший командой редактора (Vegas), не требует от пользователя
  знать, что это скрипт: он на горячей клавише и на кнопке, его правка —
  это текстовый редактор, а не пересборка. Отсюда живая экосистема:
  Excalibur, Vegasaur, Happy Otter Scripts, Montage Magic — и функции,
  которых у вендора нет.
- Расширение, живущее в процессе (Vegas Application Extension, панель
  Premiere), умеет то, чего внешний процесс не умеет в принципе:
  реагировать на изменение данных проекта, управлять воспроизведением и
  держать своё немодальное окно рядом с таймлайном.
- Транзакция (Premiere UXP) делает пачку правок ОДНИМ шагом отмены:
  пользователь откатывает работу скрипта одним Ctrl+Z, а не тридцатью.
- Внешний процесс, говорящий с живым приложением (Resolve), не требует
  закрывать проект: скрипт видит то же, что человек, и правит на глазах.
  Плюс `-nogui`: та же программа становится рендер-фермой.
- Модель «через формат» (FCP) не требует от редактора ни интерпретатора,
  ни API, ни совместимости с ним: язык выбирает автор скрипта, а вендор
  отвечает только за файл. Инструментов вокруг такого формата обычно
  БОЛЬШЕ, чем вокруг закрытого API, — их пишут те, кому нужно.
- Выражения (AE) переносят автоматизацию внутрь параметра: комп становится
  шаблоном, который читает JSON и перестраивается сам, без внешнего
  процесса, без запуска чего бы то ни было руками.

## Минусы

- Интерпретатор внутри процесса = отсутствие песочницы. Справка Vegas
  формулирует это прямо: «A script has the power to delete files, read
  files, write files, execute programs, access the Internet, access files
  on your network». Ответственность переносится на пользователя, который
  должен читать чужой C# перед запуском.
- Объектная модель становится публичным контрактом: убрал свойство —
  сломал чужие скрипты и свои штатные (Batch Render Timer, 2026). Пункт
  «вернуть функцию в API, пусть даже пустой заглушкой» появляется в
  обсуждении сам собой.
- Экосистема — это зависимость в обе стороны. Вокруг Vegasaur на форуме
  идёт спор, поддерживается ли он вообще (бесплатная версия закрыта, про
  платную участники расходятся), и вопрос «а работает ли он с новой
  версией» становится условием апгрейда самого редактора.
- API «покрывает не всё» — не временное состояние, а норма. У Resolve
  нельзя сдвинуть и обрезать уже положенный клип и нельзя тронуть параметр
  плагина; у Premiere ретайминг недоступен НИ через ExtendScript, НИ через
  UXP; текстовые слои не поддерживались никогда. Часть операций остаётся
  только руками, и это единственный ответ, который пользователь получает.
- Две платформы одновременно (CEP + UXP) — это не переход, а раскол: они
  не смешиваются, порт делается целиком, а пока UXP не достиг паритета,
  разработчик обязан выбрать, чью половину функций потерять.
- Автоматизация «через формат» не умеет ничего, чего нет в файле:
  выделение, жесты, воспроизведение, состояние ролей, открытый проект. И
  сложность формата становится сложностью API — рациональные дроби FCPXML
  съедают у автора скрипта столько же времени, сколько сам монтаж.
- Выражения (AE) — самый дешёвый вход и самая дорогая отладка: ошибка
  живёт в одном свойстве одного слоя, а видна как «рендер идёт не так».

## Как ложится на Kinotrain

### Что уже есть

**Половина ответа существует и работает: наш родной формат — открытый
OpenTimelineIO, и питоновская библиотека `opentimelineio` уже является
нашим скриптовым API.** Это не метафора: тест 158
(`src/apps/kt-cli/tests/cross_render.rs:394`) именно так и работает —
python читает НАШ файл проекта эталонной библиотекой, конвертирует его
адаптером `mlt_xml` и отдаёт чужому движку melt на рендер
(`src/scripts/otio-mlt-venv.sh`). Сторонняя программа на постороннем языке
уже сегодня открывает проект Kinotrain, ходит по дорожкам, клипам, меткам,
переходам и эффектам и получает осмысленный результат.

Опоры этого пути в коде:

- `src/libs/kt-otio/src/lib.rs` — `load_project` (стр. 78) и
  `save_project` (стр. 90); формат описан в `docs/file-format.md`, тонкости
  — в `src/libs/kt-otio/CLAUDE.md`.
- **Идемпотентность записи** (тест 144): `write(parse(write(x))) ==
  write(x)` байт-в-байт. Скрипт, который открыл и сохранил файл, не портит
  его форматированием — базовое условие для `git diff` и для цепочки из
  нескольких скриптов.
- **Passthrough «не понимать наполовину»** (тесты 145–146): неизвестные
  поля известных схем остаются на местах, объекты неизвестных схем — сырым
  JSON, **чужие неймспейсы `metadata` не трогаются вовсе**. То есть
  сторонний скрипт может положить свои данные в `metadata["myscript"]`
  любого объекта и они переживут открытие и сохранение в редакторе. Это
  наш аналог `customData` из Resolve — только не одна строка на метке, а
  структурированный JSON на чём угодно.
- **Конформанс с эталоном** — тест 149
  (`src/libs/kt-otio/tests/otio_conformance.rs`): наш файл переживает
  круг через python-библиотеку, и таймлайн, СОБРАННЫЙ питоном с нуля,
  читается нами и пересохраняется. Гейт по `python3 -c "import
  opentimelineio"`, в CI — `KT_REQUIRE_OTIO_CONFORMANCE=1`.
- **Наш конверт версионируется по СОДЕРЖИМОМУ**:
  `KT_META_VERSION = 4` (`src/libs/kt-otio/src/meta.rs:17`), а неизвестные
  kt-поля возятся passthrough'ом («форвард-милосердие», Р.29).
- `src/apps/kt-cli/src/main.rs` — headless: `version | new | demo |
  convert | roundtrip | render | export`. Экспорт полностью
  внутрипроцессный, по умолчанию на GPU (`GpuContext::new_headless()`,
  стр. 312), с возможностью прибить энкодер третьим аргументом ради
  воспроизводимости. То есть «прогнать проект без GUI» умеем уже сейчас.
- `src/libs/kt-model/src/model.rs` — `Command` (стр. 98, 45 вариантов),
  `apply` (стр. 363), **`apply_batch`** (стр. 370) и `apply_coalesced`
  (стр. 408). Транзакция «пачка правок = один шаг отмены», за которой
  Adobe шла из CEP в UXP, у нас в модели уже есть, и это готовая дверь для
  любой будущей автоматизации.

### Чего не хватает

- **В kt-cli нет ни одной команды ПРАВКИ.** `new` и `demo` создают,
  `convert` конвертирует, `roundtrip` перезаписывает, `render`/`export`
  рендерят — и всё. Нет ни `set-fx`, ни `move`, ни `split`, ни выборки
  «все клипы дорожки 2», ни отчёта в CSV. Пакетная операция сегодня
  делается только сторонним питоном, то есть требует поставить эталонную
  библиотеку.
- **Нет ни строчки документации для постороннего.** `docs/file-format.md`
  описывает формат для НАС; страницы «как автоматизировать Kinotrain» с
  примером на десять строк не существует, и человек, который хочет
  переименовать сорок клипов, об этой возможности просто не узнает.
- **Экспорт из kt-cli игнорирует регион** — сознательное расхождение с
  GUI, прямое решение пользователя в Р.34 («kt-cli и регион — не делаем»,
  `docs/user-feedback.md`). Для сценария «отрендерить по куску на каждую
  метку» это ровно тот кирпич, которого не хватает, и трогать его без
  новой просьбы нельзя.
- **Работа с ОТКРЫТЫМ проектом невозможна, и это не просто «неудобно».**
  `src/apps/kt-app` не следит за своим файлом на диске, перечитывания
  нет, IPC/сокета нет. Хуже: фоновый автосейв пишет В САМ ФАЙЛ ПРОЕКТА
  (`let target = self.project_path.clone().unwrap_or_else(autosave_path)`,
  `src/apps/kt-app/src/app.rs:1016`), то есть правку скрипта он молча
  затрёт своей версией модели. Путь через формат честно работает только
  при закрытом проекте.
- **Нет реакции на действия пользователя и нет своих панелей UI** — того,
  ради чего в Vegas существуют Application Extensions, а в Premiere и FCP
  панели.

### Что мешает

Не объём кода, а четыре упора.

**Первый — инвариант №11 (детерминизм).** Аудио байт-в-байт всегда, видео
на CPU — против закоммиченного эталона. Скрипт, исполняемый ВНУТРИ рендера
(модель выражений AE), делает картинку зависимой от версии интерпретатора,
от порядка вычислений и от всего, что автор выражения туда принесёт;
`GOLDEN_AUDIO`/`GOLDEN_VIDEO` перестают быть якорем. Скрипт СНАРУЖИ,
который только переписывает `.otio`, этого инварианта не касается вообще:
на вход движка всё равно приходит обычный файл проекта.

**Второй — инварианты №2 и №5.** FX-состояние трогает только
аудио-render-поток, декодером владеет ровно один MediaWorker. API к ЖИВОМУ
проекту (модель Resolve/Premiere) потребовал бы потокобезопасной двери в
модель — сегодня она мутируется только из UI-потока через
`apply`/`apply_batch` с undo-снапшотами. Premiere эту же проблему решил
явной блокировкой (`lockedAccess`) — то есть нам пришлось бы завести своё
такое же, и это уже не «добавить команду в CLI», а новая дисциплина
доступа к модели.

**Третий — правила UI 20 и 17.** Правило 20: «ничего не отрастает и не
отрубается само; редактирование меняет ровно то, за что тянул
пользователь». Скрипт ПО ОПРЕДЕЛЕНИЮ делает то, чего пользователь не
нажимал, — и это законно ровно до тех пор, пока он запущен явно и его
результат отменяется одним шагом. Правило 17 (парные способы одного
действия ведут себя одинаково) даёт готовое конструктивное требование:
всё, что умеет скрипт, обязано быть `Command`, иначе получим две правды о
модели — жест и скрипт, расходящиеся в мелочах.

**Четвёртый упор — требование пользователя, и его надо прочитать точно, а
не удобно.** Дословная формулировка в `docs/user-feedback.md` (раздел
«Сквозные требования»): **«никакой своей сборки FFmpeg и никаких
плагинов»**; та же фраза повторена в `docs/architecture.md:73`. Строка в
таблице называется «Системный FFmpeg» и закреплена за инвариантом №10,
поэтому «плагины» там по контексту — плагины FFmpeg. Это уже разобрано в
F-EXT-001, и вывод оттуда переписывать нечестно: **буквального запрета на
скрипты в этой фразе НЕТ**, и закрывать вопрос цитатой было бы подлогом.

Работает не буква, а причина, названная в F-EXT-001: пользователь просил
одну программу, которая на чужой машине работает тем, что на этой машине
есть, и не тащит с собой чужой бинарный багаж. На встроенный интерпретатор
эта причина ложится целиком — это чужой код в нашем процессе, со своим
жизненным циклом, своей версией и своей совместимостью, за падение
которого отвечаем мы. На скрипт СНАРУЖИ, который только читает и пишет
JSON, она не ложится вообще: в наш процесс не грузится ничего, а наличие
питона на машине — дело автора скрипта. Проверка кодом это состояние
подтверждает: `libloading` в workspace ровно один раз, в
`src/libs/kt-ffmpeg`, а интерпретаторов (`rhai`, `mlua`, `pyo3`,
`deno_core`, `boa_engine`, `wasmtime`) в манифестах нет ни одного. То
есть требование не запрещает автоматизацию — оно вместе с инвариантами
ВЫБИРАЕТ за нас, какая из четырёх моделей наша. Смежная заметка про
OFX/VST-хосты — F-EXT-001.

### Какие инварианты задевает

Путь «через формат + kt-cli» не задевает **ни одного** инварианта: файл на
входе и файл на выходе, тот же `load_project`/`save_project`, тот же
рендер. №11 цел (детерминизм считается от файла), №2 и №5 не при чём (нет
второго потока в движке), №9 и №10 не при чём (никакого чужого кода в
процессе). Единственное, что придётся соблюсти при добавлении команд
правки в kt-cli, — правило UI 17: команда CLI обязана быть тем же
`Command`, что и жест, а не второй реализацией.

Путь «встроенный интерпретатор» задевает №11 (детерминизм рендера), №2 и
№5 (доступ к модели и FX-состоянию из чужого потока), №3 (правка модели не
уничтожает FX-состояние — скрипт легко сделает то, чего не делает ни один
жест), плюс правила UI 17 и 20.

## Оценка

| Что | Ответ |
|---|---|
| Объём | M — 2 стадии: команды правки и выборки в kt-cli + страница документации с примерами на python. Вариант «встроенный интерпретатор» — XL и отдельная заметка |
| Где основная работа | kt-cli (разбор аргументов, выборка объектов, вывод отчёта), docs (страница «автоматизация»); kt-otio и kt-model не трогаются — вся механика уже есть |
| Формат проекта | не трогает: команды правки ходят через тот же `Command` и тот же писатель, версия конверта не двигается |
| Тесты, которые придётся написать | cli-тесты на каждую команду правки (результат == тот же `Command` из GUI); расширение теста 149 сценарием «python правит наш файл — мы его открываем без notices»; тест 144 (идемпотентность) остаётся эталоном; golden-тесты рендера не трогаются |
| Зависит от | ничего. Формат, конформанс с эталонной библиотекой и headless-рендер уже на месте |
| Ломает совместимость | нет |

## Вердикт

**Наш путь — второй: документировать и укрепить автоматизацию через
`.otio` + kt-cli, встроенный интерпретатор не заводить.** Сравнение
прямое. Интерпретатор внутри процесса даёт то, чего форматом не выразишь
(реакция на действия, свои панели, работа с открытым проектом), но платит
инвариантами 11, 2, 5 и 3, публичным контрактом объектной модели на годы
вперёд (у Vegas от одного убранного свойства сломался его же штатный
скрипт) и причиной, по которой отвергнут F-EXT-001: чужой код в нашем
процессе, за падение которого отвечаем мы. Путь через формат у нас уже
наполовину пройден и не стоит НИ ОДНОГО инварианта: файл
открытый и стандартный, запись идемпотентна, чужие метаданные проходят
насквозь, конформанс с эталонной питоновской библиотекой закрыт тестом, а
рендер без GUI работает. По сравнению с FCP, у которого XML — лишь файл
ОБМЕНА и Apple честно пишет, что он не заменяет родной проект, у нас OTIO
и есть родной проект: терять при круге нечего, второго формата не
существует.

Доделать надо ровно две вещи, и обе дешёвые. Первая: команды ПРАВКИ и
выборки в kt-cli — сегодня он умеет только создавать, конвертировать и
рендерить, и «поменять параметр у всех клипов дорожки» приходится делать
сторонним питоном. Вторая: страница документации с рабочими примерами —
без неё возможность существует, но о ней никто не знает. Отдельно стоит
зафиксировать честное ограничение: пока проект ОТКРЫТ в редакторе,
внешняя правка файла небезопасна (фоновый автосейв перезапишет), и это
надо написать словами, а не оставить пользователю на выяснение.
