# F-RES-001 — Автосейв и версии проекта — поверх файла или рядом с ним

## Суть

Программа сохраняет работу сама. Вопрос ровно один и он не про интервал:
КУДА она пишет. Пишет ПОВЕРХ файла пользователя — на диске всегда ровно одно
состояние, свежее и целое; защита от падения есть, защиты от собственной
ошибки нет вовсе. Пишет РЯДОМ — на диске лежит кольцо датированных копий,
и «вчерашний вариант» существует как файл. Отсюда всё остальное: сколько
копий хранить, чем их прореживать, где их искать и почему после закрытия
программы отката больше нет.

## У кого и как

| Редактор | Версия | Как называется | Как устроено |
|---|---|---|---|
| VEGAS Pro | 2026 | Auto Save (легаси) + Advanced Backup | Рабочий `.veg` не трогает ни один из двух механизмов. Легаси-автосейв пишет `.autosave.veg` в отдельный каталог и сам за собой убирает: «files are deleted when you exit the application» — это сеть под падение, а не история, по замыслу. Advanced Backup — вторая, независимая подсистема: «The creation of automatic backups begins when a change is made to the project», каталог на выбор (временный / каталог проекта / свой), прореживание ярусами — minutely «only stored within the last hour» (при шаге по умолчанию 10 мин это 6 файлов), hourly «within the last 10 hours», daily и real-time до 500 с вытеснением старых |
| Adobe Premiere | 26.x | Auto Save + Maximum Project Versions | Автосейв пишет ОТДЕЛЬНЫЕ файлы в каталог «Adobe Premiere Pro Auto-Save» рядом с проектом (кнопка Custom переносит его куда угодно); рабочий файл не переписывается никогда, и индикатор несохранённого от автосейва не гаснет. «Maximum Project Versions» — плоское кольцо, по умолчанию 20, при достижении вытесняется самый старый [вторичный источник: `helpx.adobe.com` из этого окружения не открывается] |
| DaVinci Resolve | 21 | Live Save + Project Backups | Единственный, кто пишет рабочее состояние НЕПРЕРЫВНО, — но пишет его в базу проектов, а не в файл пользователя: файла проекта у пользователя просто нет. Копии — отдельная подсистема по схеме GFS (grandfather-father-son) в своём каталоге, и там прямо сказано: «Opening a project backup does not overwrite the original project; project backups are always opened as independent projects». При простое новые копии НЕ пишутся, чтобы не вытеснить полезные бесполезными |
| Final Cut Pro | 12.3 | автосохранение библиотеки + Final Cut Backups | Сохранения как действия нет: «automatically saves all the changes you make as you work on a project», то есть рабочая библиотека переписывается непрерывно. Ответ на это — отдельные копии: «Backups include the database portion of libraries only, not the media files», имя несёт дату и время, каталог по умолчанию — Movies, старые удаляются по возрасту. Плюс Snapshot Project — версия по команде человека, а не по таймеру |
| After Effects | 26.x | Auto-Save + Increment and Save | Автосейв кладёт копии в свой подкаталог (рядом с проектом либо в указанный), «Maximum Project Versions» ограничивает их число, рабочий файл не переписывается [вторичный источник: тот же]. Именованная версия — File → Increment and Save: тот же файл с номером +1, рядом. Автоматически поверх рабочего файла в AE не пишет ничто: единственная запись «поверх» — та, которую человек заказал сам |

**Вне ядра.** Без Kdenlive эту заметку написать нельзя: у пяти редакторов ядра
публичного трекера нет, и цена их устройства не видна счётом. Kdenlive —
единственная программа, у которой механизм сохранности одновременно
задокументирован и наблюдаем в трекере, и «Фишка фишки» ниже опирается прямо
на его устройство.

| Программа | Версия | Как называется | Как устроено |
|---|---|---|---|
| Kdenlive | 26.08.0 | Backup + Project → Open Backup File | «A backup file is automatically created each time you save your project» — триггер не таймер, а команда «Сохранить». Прореживание ярусное и щедрое: «Kdenlive keeps up to 20 versions of your project file in the last hour, 20 versions from the current day, 20 versions in the last 7 days and 20 older versions». Лежит всё это НЕ рядом с проектом, а в скрытом `.backup` внутри данных приложения (`~/.local/share/kdenlive/.backup/`), и добраться до него можно только через диалог Project → Open Backup File |

## Фишка фишки

**1. Глубину отката задаёт не «сколько хранить», а ТРИГГЕР — и в списке
возможностей его нет ни у кого.** Настройка называется «Maximum Project
Versions», читается как настройка удобства и на самом деле отвечает на другой
вопрос: сколько СВОИХ ошибок пользователь сможет отменить завтра, когда undo
уже умер вместе с процессом. Но произведение «шаг × число копий» — это окно
только у таймерного триггера. У Kdenlive прореживание самое щедрое из всех
(80 копий четырьмя ярусами), а триггер — сохранение, и потому в трекере лежит
ровно то, что из этого следует: человек два часа рендерил, машина перегрелась,
резервных копий за эти два часа ноль, потому что за два часа он ни разу не
нажал «Сохранить». Vegas ставит триггером «when a change is made to the
project», Premiere и AE — таймер, Resolve — таймер с ПОДАВЛЕНИЕМ на простое,
чтобы одинаковые копии не вытеснили из кольца полезную. Четыре разных ответа
на вопрос, которого нет ни в одном сравнении возможностей, и именно он решает,
существует ли версия в ту минуту, когда она понадобилась.

**2. Каталог копий — выбор между «не найдут» и «засрут», и оба неверных
ответа лежат в трекерах открытым текстом.** Pitivi писал копии рядом с
проектом, и первым же следствием стала просьба их спрятать: «creates foo~.xptv
files littering my hard drive». Kdenlive спрятал — в скрытый `.backup` внутри
данных приложения, — и получил обратную сторону: в открытой задаче 2026 года
человек спрашивает, почему предложенное восстановление не открывает проект,
хотя выбор той же копии руками из списка открывает («why the unrecoverable
project is not listed?»). Premiere и AE выбрали середину — именованный
подкаталог рядом с проектом, — и заплатили третьим: открыв хорошую копию, ты
редактируешь ВНУТРИ каталога автосейва, и следующий автосейв перетирает её
(разобрано в F-PRJ-002 вместе с форумной инструкцией «первым делом SAVE AS»).
Ни одного бесплатного варианта тут нет, и выбор места — не оформление, а
третье по важности решение после «поверх/рядом» и триггера.

**3. Кольцо версий и recovery-файл — РАЗНЫЕ объекты с противоположным сроком
жизни, и их постоянно принимают за один.** Легаси-автосейв Vegas удаляет свои
файлы при нормальном выходе: он обязан исчезнуть, иначе при следующем запуске
предложит восстановить то, от чего человек сознательно отказался. Advanced
Backup обязан пережить нормальный выход, иначе он не история. Pitivi просил
ровно этот раскол ещё в 2010-м: «Run sanity checks when pitivi exits normally,
and if everything passes, delete the backup file». Отсюда неочевидное
следствие для того, кто пишет ПОВЕРХ: у него обе роли исполняет один объект —
файл пользователя, — и глубина отката на диске равна нулю по построению.
Восемьдесят шагов undo в памяти и ноль шагов на диске разделены не настройкой,
а границей процесса: пока программа жива, откатить можно почти всё; после
закрытия — ничего, причём именно потому, что программа старательно
сохраняла.

## Плюсы

- Кольцо рядом переживает процесс: единственная глубина отката, которая не
  умирает вместе с undo-стеком в памяти.
- Копия — обычный файл проекта, открывается тем же кодом, что и проект; ни
  формата, ни второй подсистемы чтения не нужно.
- Предел кольца делает расход диска предсказуемым и конечным: «20 версий» —
  это верхняя граница, а не «папка растёт».
- Подавление записи на простое (Resolve) сохраняет кольцу полезность: без
  него достаточно уйти на обед, чтобы двадцать одинаковых копий вытеснили
  ту единственную, ради которой всё заводилось.
- Ярусное прореживание за тот же диск отвечает и на «что было десять минут
  назад», и на «что было во вторник» (механика разобрана в F-PRJ-002,
  «Фишка фишки» 3 — здесь не переоткрывается).
- Рабочий файл, которого автосейв не касается, оставляет честным индикатор
  несохранённого: звёздочка гаснет только от команды человека.

## Минусы

- Дисковый трафик умножается на число копий, а сериализация проекта — не
  бесплатная операция; у нас это уже фоновый поток, но каталог версий
  превращает 30-секундный такт в постоянную запись.
- Открытая копия лежит внутри служебного каталога, и следующий автосейв
  перетирает её: механизм спасения работает против пользователя, если не
  запретить редактирование «из кольца» явно.
- Спрятанный каталог не находят (Kdenlive), не спрятанный — засоряет рабочую
  папку (Pitivi). Третьего места не существует.
- Версия проекта — не версия материала: копия ссылается на те же файлы, и
  откат на вчера не вернёт переименованный или перезаписанный исходник.
- Непрерывная запись рабочего состояния (Resolve Live Save, FCP) снимает
  вопрос «сохранил ли я» и вместе с ним — понятие точки сохранения: откат
  возможен только к копии, никогда к «последнему Ctrl+S».
- Кольцо ничего не знает о смысле: двадцать копий последнего часа не
  заменяют одной именованной версии «вариант для заказчика» (это отдельная
  половина, она у F-PRJ-002).

И класс «программа сама переписала мой проект, и в нём стало меньше»,
подтверждённый триажёром как `grave` и открытый третий год:

> Most recent added effects to the clip in any other sequence are missing if
> kdenlive alters project file.
> — Balr Gend, 25.06.2023, CONFIRMED, kdenlive 23.04.2,
> https://bugs.kde.org/show_bug.cgi?id=471428

СИГНАЛ: потеря сохранённого — 17 задач в kde-bugzilla, `(save|saved|saving|autosave|backup).*(lost|lose|corrupt|overwrit|gone)|(lost|corrupt|overwrit).*(project file|save)`; доля 0.3% против 0.1% в kde-invent

Второе число — то, ради которого тема вообще стоит заметки. По
`tracker-rank.py --themes` у темы «потеря данных» плотность ВХОДЯЩИХ ДУБЛЕЙ
16 на 211 задач = 7.6 % — первое место в лексиконе наравне с
«аппарат/драйвер» и втрое выше соседней темы «проект/файл» (8 на 346 =
2.3 %), при том что «проект/файл» в полтора раза больше. Дубль — самый
дорогой сигнал в этих данных (в весе он идёт ×5): он значит, что человек
напоролся НЕЗАВИСИМО, а триажёр подтвердил, что это то же самое. То есть
класс не «редкий и страшный», а «повторяемый»: люди приходят с ним по одному
и об одном и том же. Разница долей 0.3 % против 0.1 % читается так же
трезво: жалобы «сохранил и потерял» живут в пользовательском баг-трекере, а
в трекере разработки их втрое меньше — этот класс приносят снаружи, изнутри
его не замечают.

Заброшенность у темы умеренная и от этого более неприятная: открытых задач
21, медиана 2.1 года, семь старше трёх лет, максимум 5.9. Доля настоящих
фиксов среди закрытых — 0.67, то есть треть закрытого закрыта не починкой
(«закрыто» ≠ «починено», `_trackers.md`, «Как читать эти числа», п.1).

## Как ложится на Kinotrain
CAPABILITY: openspec/specs/durability/ — контракт в `spec.md`, «почему» и пути в коде в `design.md`.
Автосейв пишет в recovery-каталог, не в проект (решение владельца); вторая копия и восстановление по времени.
АДРЕС: `src/apps/kt-app/src/app.rs:1063` — класс «программа сама переписала мой проект» у нас возможен ровно потому, что цель фоновой записи вычисляется как `self.project_path.clone().unwrap_or_else(autosave_path)`: именованный проект каждые 30 с перезаписывается своим же автосейвом, и не ловит этого ничто. `write_project_atomic` (`app.rs:4939`) гарантирует, что файл целый, а `write_project_guarded` (`app.rs:4924`) — что он не старше модели; ни один из двух не хранит того, что было ДО. Тесты t194 и t199 (`layout_tests.rs`) проверяют фоновость и невозврат ревизии назад — то есть стерегут качество записи поверх, а не наличие второго состояния на диске.

## Оценка

| Что | Ответ |
|---|---|
| Объём | M — 2–3 стадии. Делится: цель автосейва + кольцо копий с пределом (S); каталог, настройка и прореживание ярусами (S); окно «Открыть копию» с датой и временем + запрет править «из кольца» (M) |
| Где основная работа | kt-app (`app.rs`: цель записи, кольцо, вытеснение, окно списка, разведение ролей recovery/история), i18n ×5 каталогов; kt-otio не трогается вовсе |
| Формат проекта | не трогает: копия — обычный `.otio`, `KT_META_VERSION` остаётся 5 |
| Тесты, которые придётся написать | kt-app `layout_tests.rs`: рабочий файл НЕ переписывается фоном при включённых версиях; кольцо не превышает предела и вытесняет самый старый; звёздочка НЕ гаснет от записи копии (правило 5, переписывает гейт t194/t200); окно копий открывается повторно (правило 14) и называет путь и время (правило 19); «открыть копию» не оставляет пользователя редактировать внутри каталога копий; t199 (сторож ревизии) обязан остаться зелёным без правок |
| Зависит от | ничего. Смежные: F-PRJ-002 (`project/history/versions-and-snapshots.md` — внутрисессионная история правок и именованные версии по команде человека; граница описана в её «Сути»), F-HLP-014 (сообщение о восстановлении) |
| Ломает совместимость | нет |

## Вердикт

Берём, и берём как развилку, а не как настройку: сегодня фоновый автосейв
пишет ПОВЕРХ файла пользователя, поэтому глубина отката на диске равна нулю
по построению, и восемьдесят шагов undo превращаются в ноль ровно в момент
закрытия окна. Все шесть сравниваемых программ — включая обе, у которых
рабочее состояние тоже пишется непрерывно (Resolve, FCP), — отвечают на это
одним и тем же: отдельным кольцом копий, которое рабочего файла не касается.
Цена у нас необычно мала — цель записи вычисляется одной строкой
(`app.rs:1063`), запись атомарна и уже фоновая, проект — один текстовый файл,
годный на роль копии без единой правки формата, а инвариантов не задевается
ни одного. Дорога здесь не механика, а дисциплина: предел кольца в коде
(правило 20), честная звёздочка при записи рядом (правило 5, переписывает
гейт t194/t200) и адрес каталога в интерфейсе (правило 19) — без этих трёх
получится ровно то, на что жалуются в трекере: копии есть, а найти их нельзя.
Именованные версии и панель истории сюда не входят и остаются за F-PRJ-002.
