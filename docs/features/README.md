# Фичи чужих редакторов и наши будущие

`docs/porting-notes.md` отвечает на вопрос «какой дефект и каким тестом закрыт»,
`docs/user-feedback.md` — «чего хотел пользователь и почему решение именно такое»,
`docs/architecture.md` — «как устроен движок», `CLAUDE.md` крейтов — «как теперь
писать код». Этот каталог отвечает на вопрос **«что умеет чужой редактор, за счёт
какой НЕОЧЕВИДНОЙ детали это работает и что из этого берём мы»**.

Заведён в Р.36 (`docs/user-feedback.md`), решение и его обоснование — п.245
`docs/porting-notes.md`. Повод: морферы придуманы изнутри, а потом выяснилось, что
в Vegas есть Adjustment Events, и там у слоя ЕСТЬ ползунок прозрачности наложения,
а у нас нет. Такие расхождения надо находить до того, как о них расскажет reddit.

**База организована ПО ФИЧАМ, а не по редакторам.** Одна фича — одна заметка,
сравнение пяти редакторов живёт внутри неё таблицей «У кого и как». При оси по
редакторам одна и та же фича описывалась бы пять раз, и вердикту «берём/не берём»
негде было бы жить.

## Правила ведения (обязательно для агентов)

1. **Читать ПЕРЕД работой над новой ФУНКЦИЕЙ** (не дефектом). Есть заметка —
   читать «Вердикт» и «Как ложится на Kinotrain»; нет — сначала завести заметку,
   потом писать код.
2. **Одна заметка = одна «фишка фишки».** Раздел обязателен и обязан содержать
   деталь, которой НЕТ в списке возможностей на сайте продукта. Нечего написать —
   заметку не заводить, вместо неё строка в таблице покрытия «проверено, своего
   ничего». Список фич есть в википедии, эта база нужна не для него.
3. **Версия и дата обязательны.** Единый справочник — `docs/features/_editors.md`,
   он обновляется ПЕРВЫМ при новой волне заметок.
4. **Цитата — дословная, ≤ 2 предложений, со ссылкой и датой.** «Пользователи
   жалуются» — не фидбек. Отрицательный фидбек не менее ценен, чем восторги.
5. **«Как ложится на Kinotrain» — с путями в коде** (`src/…`) и номерами
   инвариантов (1–12 корневого `CLAUDE.md`) либо правил UI (1–20
   `src/apps/kt-app/CLAUDE.md`). Без этого заметка не отличается от обзора.
6. **Статус `отвергнуто` — только с причиной** в разделе «Вердикт». Причина
   переживает автора; «не надо» — не причина, и через год кто-то заведёт заметку
   заново.
7. **Статус `сделано` замораживает заметку.** Тело больше не редактируется — она
   становится историческим документом «почему решили так»; живут только шапка и
   «Вердикт». Дальнейшая жизнь фичи — в `docs/porting-notes.md`. Без этого правила
   база превратится во вторую документацию продукта и разойдётся с кодом.
8. **Заметка не проектирует реализацию.** Разведка, оценка, вердикт — да; схема
   данных и порядок стадий — в раунде. Иначе получим полсотни протухших полу-ТЗ.
9. **Файлов-заглушек не бывает.** Файл появляется, когда заметка написана;
   непокрытое видно по таблице ниже. Иначе `grep` перестанет отличать сделанное
   от запланированного.
10. **После каждой партии — `python3 src/scripts/features-index.py --check`**
    и обновление таблицы покрытия. Сводная таблица вставляется РУКАМИ из
    `--table`: в репозитории нет ни одного генерируемого markdown (правило 20
    чек-листа — ничего не отрастает само).

## Шапка заметки

YAML-frontmatter — единственное место в `docs/` с machine-readable форматом;
заведён по прямому решению Р.36 («создать бд»). Словари закрытые, `--check`
проверяет:

| Поле | Значения |
|---|---|
| `id` | `F-<КОД>-<NNN>`, номер сквозной внутри категории, не переиспользуется |
| `status` | `исследовано` · `кандидат` · `принято` · `в-работе` · `сделано` · `отвергнуто` · `уже-есть` |
| `priority` | `A` — без этого продукт не считается видеоредактором · `B` — заметная потеря, монтажёр обходит · `C` — нишевое |
| `cost` | `S` — одна стадия раунда · `M` — 2–3 · `L` — целый раунд · `XL` — раунд плюс изменение формата или инварианта |
| `we_have` | `да` · `нет` · `частично` |
| `editors` | ключи из `_editors.md` |
| `invariants` / `ui_rules` | номера из корневого `CLAUDE.md` / `src/apps/kt-app/CLAUDE.md` |
| `round` / `point` / `tests` | заполняются, когда фича принята и сделана |
| `checked` | дата проверки; `--check` ругается на давность > 18 мес. при статусах `кандидат`/`принято` |

**ID — адрес, путь — ярлык.** Заметку можно переименовать и переложить в другую
подкатегорию, ID не меняется: он попадает в сообщения коммитов
(`Кривые RGB и Luma (F-CLR-002, п.253, Р.37 С1)`), где путь
`docs/features/color/primary/curves-rgb-and-luma.md` нечитаем.

## Категории

| Каталог | Код | О чём | Написано / план |
|---|---|---|---|
| `morpher/` | MPH | adjustment-слои: наше против чужого | 0 / 8 |
| `color/` | CLR | цветокоррекция, scopes, LUT | 0 / 6 |
| `masks/` | MSK | маски, кеинг, трекинг, стабилизация | 0 / 6 |
| `audio/` | AUD | обработка и микширование звука | 0 / 5 |
| `timeline/` | TL | операции над событиями, структура монтажа | 0 / 5 |
| `titles/` | TXT | титры, генераторы, субтитры | 0 / 4 |
| `time/` | SPD | скорость, ретайминг, синхронизация | 0 / 4 |
| `automation/` | AUT | ключи, кривые, пресеты | 0 / 4 |
| `media/` | MED | организация медиа, прокси, источники | 0 / 3 |
| `export/` | EXP | пресеты, очередь, smart render | 0 / 3 |
| `project/` | PRJ | секвенции, история, версии | 0 / 2 |
| `ui/` | UI | вьюер, ввод, раскладки | 0 / 2 |
| `plugins/` | EXT | OFX/VST-хосты, скриптинг | 0 / 2 |

Подкатегория — стабильная таксономия, объявленная здесь; она не создаётся и не
удаляется под настроение. Каталоги не нумеруются (`01-timeline/`): добавление
категории перетасовало бы все пути.

`morpher/` — единственная категория с подкатегорией `gaps/` (чего не хватает
НАШЕМУ). Это единственное место, где мы впереди рынка, и разница с Vegas/AE —
повод всей работы.

## Где искать

Порядок доверия и конкретные площадки — в `docs/features/_editors.md`, раздел
«Как проверять». Поводом для заметки часто служит чужая фраза «перешёл на новую
версию из-за X» — именно она означает, что фича стоит денег, а не строчки в
списке возможностей.
