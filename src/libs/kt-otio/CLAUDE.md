# kt-otio

> Контракты крейта и обязательные тесты — `openspec/specs/{project-format}/spec.md`, причины решений — `design.md` рядом.

**С Р.70 OpenTimelineIO — формат ОБМЕНА, не проекта.** Файл проекта — свой
`.kt` (`kt_model::project_file`), а этот крейт — две названные двери
(`import_interchange` ← `File → Import older Kinotrain project…`,
`save_project` ← `File → Export → OpenTimelineIO…`), детект вида файла по
содержимому (`detect`: свой / OTIO / легаси) и единственный дом атомарной
записи (`write_atomic`). Всё ниже про идемпотентность, passthrough и версии
конверта — про ДВЕРИ, и остаётся в силе. Чистый Rust (serde_json), БЕЗ
FFmpeg/аудио/C++-биндингов/url-крейта. Зависимости: kt-time (+kt-model с
этапа convert). Эталон семантики — C++/Python библиотека OTIO 0.18.x.

## Инварианты

- **Идемпотентность записи** (тест 144): `write(parse(write(x))) == write(x)`
  байт-в-байт. Байт-passthrough ЧУЖОГО файла не обещаем — первое сохранение
  нормализует форматирование (так делает и эталон); неизменность гарантируется
  для содержимого, не для пробелов.
- **Passthrough, «не понимать наполовину»** (тесты 145-146): неизвестные ПОЛЯ
  известных схем — в `#[serde(flatten)] extra` на исходных местах; объекты
  неизвестных схем/версий-листьев — `RawObject` verbatim; чужие
  metadata-неймспейсы нетронуты, наш `"kt"` дописывается в конец. Версия
  ХРЕБТА (Timeline/Stack/Track) новее поддерживаемой → жёсткий отказ
  (позиции детей стали бы догадкой) — проверяется префлайтом по сырому Value:
  serde-мост превращает типизированные ошибки в `Json(custom)`, поэтому
  отказ хребта ДО `typed()`-парса, не внутри.
- **Канонический порядок ключей**: `OTIO_SCHEMA` первым, известные поля в
  порядке объявления структуры (заморожен тестами), `extra`/metadata — порядок
  документа. Требует `serde_json/preserve_order` — фича ГЛОБАЛЬНА для
  workspace (cargo unification): `serde_json::Map` везде становится IndexMap.
  Аудит на момент включения: Value жил только в тестах kt-model — безопасно;
  новые Value-потребители обязаны не полагаться на алфавитный порядок.
- **Стартовый таймкод материала (п.180)**: `source_range` и
  `available_range` — одна система координат, у вещательных файлов она
  начинается со вшитого таймкода. `source_in` модели считается ОТ ПЕРВОГО
  КАДРА файла, поэтому начало `available_range` вычитается на чтении и
  возвращается на записи. Клип без `source_range` берёт материал целиком с
  НУЛЕВОЙ точкой входа.
- **NTSC-частоты (п.178)**: 23.976/29.97/59.94 сетку 90 кГц не делят
  (90000/23.976 = 3753.75). `grid_fps` округляет их до ближайшей целой,
  делящей 90000 (иначе такой файл молча становился проектом на 30 fps).
  Склейки от этого не страдают — они в тиках; байт-стабильность круга на
  таких файлах не держится (тик на клип).
- **Время**: `RationalTime{value, rate}` — наши тики пишутся value=целое
  (двойная точность точна до 2^53), rate=90000.0; чужие rate квантуются
  `round(value*90000/rate)` — политика всей системы.
- **`OTIO_SCHEMA` на КАЖДОМ SerializableObject** — эталон отвергает голые
  словари, включая вложенные RationalTime/TimeRange (ручные Serialize с тегом,
  duration раньше start_time — порядок эталона) и Stack в `Timeline.tracks`
  (поле идёт мимо Composable-моста → serialize_with/deserialize_with; на
  чтении тег снимается, чтобы не оседать в extra). Наши тесты идемпотентности
  такое НЕ ловят (своё «неполное» прощается) — ловит только конформанс т.149.
- `metadata.kt.v` — одна версия на ФАЙЛ (Timeline); новее нашей → явный отказ
  `KtMetaTooNew`. Вложенные kt-конверты версий не несут.
- Upgrade схем: только Clip.1→2 (media_reference → media_references), как в
  эталоне. Marker.1 и прочая архаика — passthrough-лист.
- `detect()` — по СОДЕРЖИМОМУ (OTIO_SCHEMA против format_version), расширению
  не верим. .ktproj как проект не открывается (Р.24 п.12) — только импорт.
- Пути (тест 147): target_url пишется относительным (POSIX-слэши), фолбэк —
  file://-URL с percent-encoding (как Resolve/Hiero); читаются относительный /
  абсолютный / file://; `synth:` — verbatim.

- **Чужое, что формат разрешает** (п.154): клип без `source_range` берёт
  `available_range` целиком; `media_reference: null` — законный клип без
  материала (null возится round-trip'ом, ExternalReference не выдумывается);
  `name: null` нормализуется в пустую строку (как эталон).
- **Хвостовой Gap = монтажная длина** (п.158): читается в
  `Project.timeline_end`, на записи дописывается каждой дорожке короче конца.
  Пустая дорожка, которой не было в файле, НЕ пишется — число наших дорожек
  живёт в `metadata.kt.lanes`.
- **Краевой переход — фейд, а не мусор** (п.155): переход первым/последним
  ребёнком дорожки и переход рядом с Gap импортируются как `TransitionEvent`
  с пустой стороной и пишутся обратно на своё место.

- **Слои (Р.28, п.165)**: перекрытые клипы одной дорожки пишутся соседними
  `Track` (в OTIO позиция клипа = порядок детей, наложение в одном треке
  невыразимо), карта `metadata.kt.layers` хранит число треков на дорожку и
  собирает их обратно. Не сошлась с файлом — игнорируется с notice. Слой 0
  несёт имя дорожки и чужие extra/gap'ы. Без перекрытий карта не пишется, и
  файл байт-в-байт прежний.

- **Битое — отказ, чужое — passthrough (Р.49, п.358)**: НАША секция клипа
  читается `kt_get_checked`, как и у Timeline (t251). «Секции нет» — обычный
  чужой файл; «секция есть и битая» — ошибка со списком адресов ВСЕХ битых
  клипов. Молчаливое выбрасывание давало клипу новый номер и рвало link-группы
  A/V и ссылки морферов необратимо. Чужое у дорожки (`effects`, `markers`,
  `enabled`) и у метки (`comment`, `metadata`, `extra` —
  `Retained.stack_marker_extras`) возвращается на место; выключенная чужая
  дорожка даёт notice. `Clip.enabled` не чинится — он уже verbatim через
  ForeignEvent. Тесты 383-386.

- **Ссылки на материал — свойство МЕДИА (Р.49, п.356)**: `Retained.media`
  (`HashMap<MediaId, MediaRefs>`) наполняется на чтении и служит запасным
  путём на записи для клипов, РОЖДЁННЫХ в редакторе (половина разреза, кусок
  bake, вставка, событие из бина) — у них своего `ClipExtra` нет. Без этого
  две половины одного разреза уезжали в файл в разных системах координат:
  левая от вшитого таймкода, правая от нуля. Свой конверт клипа медиа-уровень
  НЕ перетирает (чужой `active_key` и набор вариантов целы). Тесты 377-378,
  `tests/edit_roundtrip.rs` — круг «загрузил → отредактировал → сохранил →
  загрузил», единственный в крейте, где правка вообще происходит.

- **Уровень события (Р.28, п.174)**: `metadata.kt.opacity` у клипа; 1.0 не
  пишется — файлы без уровня байт-стабильны.

- **Камеры и версия ПО СОДЕРЖИМОМУ (Р.29, п.189)**: `KT_META_VERSION = 2`,
  но писатель ставит v=2 только когда файл несёт камеры/камерные дорожки
  (`metadata.kt.cameras`/`camera_lanes`, сортировка по CameraId) — старый
  ридер молча потерял бы 3D-сцену при перезаписи. Файлы без камер — v1
  байт-в-байт (t144/t148 не перегенерировались). Один Pan3d версию не
  бампает (foreign-passthrough у старого ридера). Неизвестные поля НАШЕГО
  конверта (kt) — flatten-extra в KtTimelineMeta/KtClipMeta, passthrough
  через Retained (timeline_kt_extra / ClipExtra.kt_extra): добавкам v3
  жёсткий отказ не понадобится. Автоматизация FX (Р.30) — ключ `auto` внутри kt-конверта
  эффекта; её наличие тоже поднимает файл до v2. Golden v2-схемы —
  fixtures/demo-3d.otio (t189_regen; замораживает и камеры, и кривые).

- **Вид перехода (Р.33, п.222)**: `kind` и `audio` в `Transition.metadata.kt`;
  наружу — осмысленный `transition_type` (SMPTE_Dissolve/SMPTE_Wipe/Custom),
  ЧУЖОЙ тип из Retained не подменяется. Не-кроссфейд или не-дефолтная кривая
  поднимают файл до v3 (старая сборка сыграла бы вайп растворением). Возврат
  к кроссфейду ВЫЧИЩАЕТ наш конверт из retained-метаданных — иначе устаревший
  вид уехал бы обратно в файл; опустевший `kt` убирается целиком, чтобы чужой
  файл остался байт-стабильным. Тест 222.

## Старые версии читает ИМПОРТ, не ридер (Р.67, решение владельца)

- Файл конверта `v < KT_META_VERSION`, который `timeline_to_project` отвергает, идёт
  через `legacy_import::import_older(text, base)`: JSON-предобработка по таблице
  `FIXUPS` (каждая починка — с версией, для которой заведена, и с notice), затем
  обычное чтение. `load_project` в этом случае возвращает `Error::NeedsImport { version }`
  — kt-app показывает версию и пункт `File → Import older Kinotrain project…`.
- **Ридер новым старым формам не учат.** Нашёл файл, который не читается, — починка в
  `FIXUPS`, тест на синтетической копии структуры; при снятии поддержки версии её починки
  удаляются вместе с тестами. Первая: `v5_null_morph_targets` (`targets: null` ⇒ «всё,
  что ниже»). Существующие миграции в ридере (v<3 доли→тики, v4 морфер, v8 генератор,
  `ease`) остаются как есть — это правило для НОВЫХ починок.

## Р.70: двери обмена, passthrough в файле проекта

- **`import_interchange` — ОДНО правило выбора пути** на три входа: чужой `.otio` без
  нашего конверта читается обычным `load_project` (ему починки не нужны, а
  `import_older` его отверг бы — `doc_version` требует `kt.v`); наш старой версии —
  `import_older` по `NeedsImport`; легаси — `import_legacy`. Файл проекта в дверь не идёт:
  `Error::ProjectFile` называет «Открыть». Приложение и kt-cli зовут только её — две копии
  этого `match` разошлись бы на первом же чужом файле (так и нашлось: t819).
- **`Retained::to_json`/`from_json`** — passthrough едет в поле `otio` файла проекта.
  `HashMap`-поля пишутся ОТСОРТИРОВАННЫМИ ПАРАМИ `[ключ, значение]` (`sorted_pairs`):
  ключи не строки, порядок обхода случаен, без сортировки каждое сохранение — ложный дифф.
  Порядок ЧУЖИХ ключей документа при этом НЕ трогается — это обещание экспорту (t154),
  детерминизм даёт insertion-ordered `Map` (`preserve_order`). `is_empty` — «нечего
  возвращать»: такой проект поля не несёт.
- **Пути медиа: в памяти абсолютны, в файле относительны** — так было у `load_project`/
  `save_project`, и свой формат повторяет правило через `resolve_project_media`/
  `relativize_project_media` (т797: проект переезжает вместе с материалом).
- Тесты: t814 (экспорт самодостаточен, «Открыть» его отвергает), t816/t817 (круг
  passthrough), t146 (детект своего файла).
