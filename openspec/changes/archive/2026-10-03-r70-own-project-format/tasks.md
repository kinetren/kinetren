## 2. The foreign passthrough is not lost

- [x] 2.1 `kt_otio::Retained` gets `to_json`/`from_json` (reusing the existing writers and parsers, without deriving serde on seven hand-written types). Check: t816 (`src/libs/kt-otio/tests/convert.rs`) — a foreign `.otio` with unknown namespaces, markers and effects survives the round trip `Retained → JSON → Retained` field by field. **Done:** `Retained::to_json`/`from_json` via the same serde bridges of the nodes (`node_serde!`) that write and read OTIO; there is no layer of its own. `RawObject` — `#[serde(transparent)]`, derive on `ClipExtra`/`MarkerExtra`/`MediaRefs`/`TrackExtra`/`Retained`. Five `HashMap` fields travel as SORTED PAIRS `[key, value]` (`sorted_pairs`): the keys are not strings (`(ClipKind,u32)`, the pair `Option<ClipId>`), and the traversal order of a `HashMap` is random — without sorting every save would be a false diff. t816 lives in `kt-otio/tests/project_file.rs` (next to t813), and the measure of the round trip is the EXPORT byte for byte, not just equality of structures.
- [x] 2.2 The passthrough travels in the project file as a separate field and returns on export. Check: t811 (the same round trip, but with a non-empty passthrough) and t817 — import of a foreign `.otio` → saving as a project → export gives a file with the same foreign fields. **Done:** the `otio` field of the envelope, written AS IS — the order of foreign keys is part of the promise to the interchange file (t154), it cannot be sorted; determinism is provided by the insertion-ordered `Map` (`preserve_order`) plus sorting in `Retained::to_json`. The wording of 1.5 "with sorted keys" is refined: only unordered maps are sorted — to be corrected in the spec at stage 5. t817: import → `to_text` → `from_text` → export matches the direct export byte for byte, `zeta` before `alpha`; a project without the passthrough field does not carry it.
