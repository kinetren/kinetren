# Design: idle-cpu

## Context

The owner's words are in `docs/ktprompts/kkt-26.11.07.txt`. This machine has no graphics card, so wgpu
runs on llvmpipe or lavapipe and a frame costs 80 ms of processor. Percent measures that, so the
measure is WORK: `kt_time::work`, relaxed atomics that steer nothing.

The project is `kt-cli showcase --heavy`: nine releases of a composition carrying Slowed, VHS Tape and
Camera ISP, a dense edit of 1350 events under them.

## D1. What ran on a pause

| Cause | Counters on the pause (1357 events) | Since |
|---|---|---|
| The preview service evicted a live release; the frame asked again | 3.7 reel jobs, 66 submits, 15 UI frames a second; 236 % of a core against 46 % | R.59 (cap of 6 from R.56, one key per instance from R.59) |
| One sidecar row per reel | every release but the last rendered on each opening | R.59 |
| The tick of 4 Hz | 4 UI frames a second, 36 % of a core in software | v1.4 |
| An incomplete frame recomposed on every UI frame | each mouse move pays the chain; `last_compose_retry` was written and never read | R.53 |
| The meters' cap falling at 60 fps after a seek | 10 s of full frames from a level under the cursor | R.16 |

The old logic in the live scenario prints the mechanism: `over the preview: reel_jobs 74` in 74 frames.
One job per UI frame: the request runs in the frame, so the mouse drove the circle. That is the
owner's "повожу мышкой", and his "hover a composition" (the same frames, while the circle runs).

Rejected: a larger cap. Any number is a project away from the same circle; the cap's job is memory,
and what an event shows has to stay.

## D2. At rest nothing polls

The frame was the program's scheduler. `wake` replaces it: a background thread says it has something,
a clock asks for its moment (`KtApp::rest_wake`). No heartbeat: a missed wake is a defect to find, and
a heartbeat would hide it at the price of frames forever. `wake::soon` carries a stream of small
results as one frame per 120 ms, because egui keeps the earliest repaint asked for.

The bench needed the same: `live-ctl` watches its file, and a throttled dump asks for one more frame.

## D3. An incomplete frame waits for news

`BurstCache::on_next_insert` hears the next insertion; `compose_news` then checks that nothing is
missing before paying for a composite. A timer that doubles from 250 ms to 8 s remains for a
`complete = false` that comes from something other than a missing layer. Past it the frame waits for
an edit, a seek or an insertion: it costs nothing to leave it.

## D4. Hover

A hover frame costs what egui costs: there is no way to skip a frame from `App::ui`, and egui-winit
asks for one on every cursor event. What scaled with the view is the event pass. `EventPaint` keeps the
events as meshes across pure pointer frames. Measured on this machine the hover frame is 16 ms on the UI
thread, 12 of them in the software driver's queue submit (gdb samples: 22 of 35), and `draw_all` is
3.9 ms, of which the event pass is 2.5. So the visible gain here is small and the gain on a card is
that 2.5 ms plus the tessellation. The counter shows it: event passes per frame go from 1 to under a
third.

Any frame that is not a pure pointer frame drops the meshes. A stale picture would be worse than a
slow frame, and this keeps the stamp short.

## D5. The adapter

wgpu's LowPower sorts integrated first. The record in `docs/user-feedback.md` (R.31, R.32) shows the
owner's program on "AMD Radeon Graphics (RADV RAPHAEL_MENDOCINO)", the two compute units inside a
Ryzen 7000. If he also has a discrete card, LowPower took the small one, and every effect has run
there since the CPU composite was deleted on 2026-11-05. LowPower was the fix for hybrid graphics
(item 39), so it is not flipped: the question is which card drives the monitor, and sysfs says. A
discrete card alone driving them gets the work. This could not be run: there is no card here. t1837
holds the rule on facts; the load report carries the facts of his machine.

## D6. The load report

A thread of its own, so it survives a stalled UI. Writing is automatic on a load of a whole core for
three seconds, because the owner may not reach a menu. It reads `/proc/self/task` once a second; on
Windows there are no per-thread times yet. It is a local file: telemetry reads nothing from it.
