# Properties and automation

## Purpose

A single property model (parameter passport, types, clamping, addressing) and one animation mechanism for all carriers: keys in the source's material, compiled video automation, copy-paste and presets with curves, generator parameters on the event, and public composition parameters with overrides on the instance.

## Requirements

### Requirement: Parameter passport — one declaration, typed, built at runtime
The parameter specs, the write and read by name SHALL be generated by ONE declaration (a passport macro) for each carrier — effects, transition kinds, cameras, generators; the hand-written tables `param_specs`/`set_param`/`get_param` MUST NOT exist. A spec carries the name, min/max/default/step, the unit, the kind (`Smooth` — automated, `Structural` — not), and the TYPE (number, flag, color, choice, text, media); a curve is admissible only for a number and a color. The passport is returned by a reference to the owner, not as `&'static`: for a public parameter of a composition and for a plugin it is known only at runtime. The color is DERIVED from the rows `<stem>_{r,g,b,a}`, not declared separately; `Choice` is stored by the variant's key, not by its number.
Why: three hand-written tables had already diverged (different ranges of one parameter in three windows), and a static passport expresses neither an author who renames nor a plugin.

#### Scenario: The passport of each carrier is typed and without duplicates
- **WHEN** the passports of all effects, transition kinds, generators, and cameras are walked
- **THEN** the names in a passport are unique, the built-in rows are numeric and have no label of their own (the catalog provides it), the default lies within the range, and the step is positive
- **TEST** t641 (`src/libs/kt-model/tests/props.rs`)

#### Scenario: Every passport parameter is written and read
- **WHEN** for each effect kind from the registry, each spec is written and read by name
- **THEN** the value is clamped to the range, a foreign name is rejected (an orphan curve), a structural parameter does not enter the list of automatable ones, and the specs of audio effects are non-empty
- **TEST** t190 `t190_set_get_param_all_specs` (`src/libs/kt-model/tests/fx_auto.rs`)

### Requirement: The clamp lives in the passport; index addressing equals name addressing
The value of a parameter SHALL be clamped by ONE rule in the passport macro — for all owners and for both addressing paths (by name and by row index). An index outside the passport MUST be a refusal, not a panic and not a silent write.
Why: until then the clamp lived in the wrappers of effects and transitions, and generators had none at all — a title's font size accepted any number from a file and from a command.

#### Scenario: Two addressing paths give the same bytes
- **WHEN** a parameter is written by index and read by name, including a value beyond the spec's limits
- **THEN** the values read are bitwise equal, the clamp matched on both paths, and an index beyond the passport is rejected
- **TEST** t642 (`src/libs/kt-model/tests/props.rs`)

### Requirement: Key domain — the source media tick
The position of an automation key SHALL be a MATERIAL tick in the coordinate system of `source_in`, not a fraction of the event's length and not a timeline tick. The attachment to the material is ensured by the REPRESENTATION: trimming, cutting, reversing, and moving an event do not touch the curves at all; a key outside the visible piece is legitimate (hidden by trimming). The translation "timeline tick → material" is one function for the whole project (the engine, the UI, and the tests call that same function); the curve is sampled at the material position aligned to the grid of frames. The value beyond the curve's edges is the edge value; the domain is not clamped at either end. Everything that moves the read anchor `source_in` NOT together with the material (a cut under a warp, a source substitution by a morpher layer) MUST shift the keys by the same delta. Audio is automated by the same mechanism: the curves are converted into profiles once at renderer build time; slowed&reverb has no second domain.
The shape of a section lives ON THE KEY and refers to the segment after it; when an event is cut, the shape of the last key of the left half is preserved, and the value at the junction is the same from both sides.
The relation between DIFFERENT events is computed on the common denominator — the TIMELINE tick, through that same translation function; there is no second rule for translating time in the program.
Why: the domain "share of the event" was rubber (trimming the end moved the middle of the animation; Split duplicated the curve into both halves); the owner's decision — "as in Premiere".

#### Scenario: Geometry edits do not move keys
- **WHEN** an event with a curve is trimmed from both ends, split in half and reversed
- **THEN** the keys in both halves are byte-for-byte unchanged, the curve value at the cut seam is the same from both sides, and the shape of the last key of the left half is preserved
- **TEST** t212 `t212_keys_stick_to_material_through_edits` (`src/libs/kt-model/tests/fx_auto.rs`)

#### Scenario: Curve value outside the clip body

- **THEN** the extreme value is returned (a transition handle and pre-roll are legitimate), a single point is a constant, and an empty curve has no effect
- **TEST** t190 `t190_curve_value_semantics` (`src/libs/kt-model/tests/fx_auto.rs`)

#### Scenario: Old files with a fractional domain are read
- **WHEN** a file older than v3 is opened, where keys are stored as fractions of the event length
- **THEN** the keys are converted to material ticks by the geometry of their own clip (mirrored for a reversed one), and rewriting the file raises the version
- **TEST** t212 `t212_pre_v3_curves_migrate_to_material_ticks` (`src/libs/kt-otio/tests/convert.rs`)

#### Scenario: Audio by curve, same mechanism

#### Scenario: Source substitution by a layer carries the event's curves

### Requirement: One animation mechanism for all carriers
Curves of cameras and transition parameters SHALL be the same `ParamCurve` as effects use, and
are drawn by the same widget; the automation widget MUST NOT know about the clip. It receives
the specs, the axis range in the curve's domain, and a pair of functions "curve domain ↔ timeline tick". The domains
of the carriers are their own and are recorded: clip — material, camera — tick from the start of the event,
transition — tick from the start of the window; a key outside the window is legitimate, and changing the length
opens or hides keys. A curve on a nonexistent parameter fails loading. Legacy keyframes (CamMotion, cameras, slowed)
are converted on read and are never written.
Why: each carrier had its own keyframe editor (slowed — a graph, pan3d — a table), and they drifted apart;
"CamMotion with keyframes" is the "Geometry" node with curves
(before R.62 — Pan with curves).

#### Scenario: A camera is animated with shared curves
- **WHEN** a camera has legacy keyframes, and then curves of the same kind as effects use
- **THEN** the conversion gives the same values as the old mechanism; moving the camera carries its animation; an orphan curve fails validation
- **TEST** t231 (`src/libs/kt-model/tests/cameras.rs`), t231 `t231_camera_editor_opens_and_edits` (`src/apps/kt-app/src/layout_tests.rs`)

#### Scenario: Legacy CamMotion migrates to Pan curves
- **WHEN** a project with CamMotion keyframes in the old format is read
- **THEN** (the scenario heading is historical: Pan was abolished in R.62) they become the curves `pos_x`/`pos_y`/`zoom` of the "Geometry" node (not the leading one, on the same slot; `pos = pan_to_pos(pan, zoom)`), and rendering by the curves gives the same picture the old mechanism gave, within the resampling tolerance (mean deviation < 4/255; at zero with zoom 1 — byte for byte): the node stores the position and places the layer with a continuous affine transform, whereas the legacy code interpolated pan and zoom separately and cut an integer frame — byte-for-byte is unreachable by construction, and the owner did not require backward compatibility (R.62); CamMotion is not written back to the file
- **TEST** t230 (`src/libs/kt-engine/tests/fx_auto_render.rs`)

#### Scenario: Transition parameters are animated by the same widget
- **WHEN** a transition has a parameter curve of the kind (domain — tick from the start of the window)
- **THEN** the picture changes along the curve, at the start of the window the value equals the static one, and a key beyond the window edge is legitimate (the transition kind's contract — capability `transitions`)
- **TEST** t232 (`src/libs/kt-engine/tests/transitions_video.rs`)

### Requirement: Compiled video automation and zero cost
Curves of the video path SHALL be compiled ONCE, when the renderer is built, into a plan (slot,
passport row index, keys, segment shape); per frame, access is by index, with no lookup by
name and no clone of the chain. Derived sources (link, formula) SHALL be resolved in the same place
and in TOPOLOGICAL order, once per build. A clip without live curves (no
curves, a curve without keys, an orphan curve) MUST borrow the chain, not copy it.
Curves and links on one event MUST NOT change the plan of a neighbouring one. The hash of post-FX is computed from the
raw curves, before compilation, and includes the formula text and the link address: cache keys do not depend on
the addressing method, but they DO necessarily depend on the CONTENT of the source.
Why: the owner's requirement "a simple project does not lag, physics on one source does not
slow down the whole project"; for audio this rule has been in place from the very start.

#### Scenario: The plan equals the frozen named path
- **WHEN** for all kinds of effects, both ends of the range, segment shapes, reversal and orphan curves, the plan is checked against a verbatim copy of the former named path, which lives in the test
- **THEN** the numbers match bit for bit, the orphan does not compile, and the clamp matches in both paths
- **TEST** t643 (`src/libs/kt-model/tests/props.rs`)

#### Scenario: Nothing to compile means no plan
- **WHEN** the chain has no curves, the curves are empty or have no keys
- **THEN** compilation returns `None`
- **TEST** t643b (`src/libs/kt-model/tests/props.rs`)

#### Scenario: A clip without curves borrows the chain
- **WHEN** an event without curves and an event with an orphan curve are rendered
- **THEN** the layer's chain is borrowed (not copied); only the clip with a live curve copies it
- **TEST** t644 (`src/libs/kt-engine/tests/auto_plan.rs`)

#### Scenario: A neighbour's curves do not affect others
- **WHEN** one event has curves or links, and the neighbouring events do not
- **THEN** the plan of the neighbours is byte-for-byte the same as in a project without curves
- **TEST** t645 (`src/libs/kt-engine/tests/auto_plan.rs`), t705 (`src/libs/kt-engine/tests/auto_plan.rs`)

### Requirement: The chain's master switch does not destroy it
The event's `fx_off` flag SHALL switch off the active chain entirely (the engine sees neither slots
nor curves), WITHOUT touching the state of the slots, the bypass flags, or the curves; the morpher's switch does the same
for its layer. The master switch switches off the chain of the EVENT, not the layer above it. The default
(enabled) is not serialized. The command is not geometric, and undo is free.
Why: the owner's requirement "a master checkbox to disable the fx chain; in morphers likewise, everything is unified";
deleting instead of disabling would lose work.

#### Scenario: Switched off means hidden, switched on means as it was
- **WHEN** a chain with curves and a bypass slot is switched off by the master flag, and a morpher layer sits above the event
- **THEN** the active chain and curves are empty, the `fx`/`fx_bypass`/`fx_auto` themselves are intact, the layer above still applies, and undo restores it; a disabled morpher adds no effects but remains on the track
- **TEST** t214 (`src/libs/kt-model/tests/fx_auto.rs`)

### Requirement: Copy-paste of effects, chains and envelopes — one model, one paste
Blocks of the buffer (slot, chain with the donor's `src_in`, envelope with a kind tag) SHALL live in the model
and be serialized in the same form to the system clipboard. **The system clipboard SHALL be
the only source of paste**: there is no mirror of the buffer inside the program, the paste button NEVER
goes grey, the content is read ON PRESS, and content that cannot be parsed gives an error with
the reason in the status line. Paste SHALL go through ONE append function for all
carriers (event, morpher, preset): keys are re-hung "input to input" without scaling, negative time is clamped to zero, curves are extended to the length
of the chain, and the donor's `fx_off` is NOT applied to the receiver. An envelope for a DIFFERENT kind of effect SHALL
be pasted with field matching: fields matching by name and type land silently, and for the remainder
a window "curve → target parameter" opens; not a single curve is silently lost. A carrier
without curves as a type MUST NOT exist. Paste returns commands, a single undo step. When copying, the name gets
the SUFFIX "copy" by default, not a prefix.
Why: two sources of truth for one action produced silent loss of animation; a mirror of the buffer
inside the program greyed out the button based on content copied in another window — a state
that must not exist (the owner's complaint, R.61).

#### Scenario: Slot, chain and envelope survive the buffer
- **WHEN** a chain with slots, bypass and keys, a separate slot and an envelope are copied, and the block is round-tripped through JSON
- **THEN** the chain is pasted onto the target's material as one undo, the slot is appended at the end, the envelope lands in its kind, and the block equals itself after the round trip
- **TEST** t215 (`src/libs/kt-model/tests/fx_auto.rs`)

#### Scenario: One paste function for an event and a morpher
- **WHEN** an event block is pasted into a morpher (input = 0) and back into the event with a different input point, then a second block is appended
- **THEN** the keys are counted from the donor's input point in both directions, the slot state moves over, `fx_off` is not inherited, and the second block lands at the end in parallel with the curves
- **TEST** t342 (`src/libs/kt-model/tests/fx_auto.rs`)

#### Scenario: Pasting into a morpher window carries curves
- **WHEN** a chain with a curve from the buffer is pasted into the morpher window
- **THEN** the keys have moved and are recalculated into the block's domain
- **TEST** t343 (`src/apps/kt-app/src/layout_tests.rs`)

#### Scenario: The copy is named with a suffix
- **WHEN** a named item is pasted through the prefix window with its defaults
- **THEN** the name gets the suffix "copy" (the prefix is a switch in the same window), and repeat numbering goes through a shared unique name
- **TEST** t263 (closed in `t250_paste_prefix_dialog`, `src/apps/kt-app/src/layout_tests.rs`), t249 (`src/libs/kt-model/tests/morph_slice.rs`)

### Requirement: Warp speed is shared by the A/V link pair
The presence of a warp slot, `rate`, and the curve `"rate"` SHALL be mirrored across the link group inside
model mutations (`SetFx`/`SetFxAuto`/`SetFxBypass`), not in the FX window; the slot is looked up BY KIND,
not by index. Each has its own: the reverb parameters, the frame mode, the slot's bypass. A break of the
group stops the synchronization; linking does NOT align retroactively. A single clip
is not affected by the rule.
Why: `SetFx` comes from the buffer, the morpher bake, the format reader and kt-cli — a UI-only rule
would be bypassed by all of them; "a pair consumes the source at one speed" is an editing invariant.

#### Scenario: Editing speed moves to the partner in one undo
- **WHEN** a warp slot and the rate curve are added/edited/deleted on one of a pair, and then the group is broken
- **THEN** the partner receives the same thing in one history step, the partner's mix curve and reverb are untouched, and after the break there is no synchronization
- **TEST** t248 `t248_warp_rate_is_shared_by_the_link_group` (`src/libs/kt-model/tests/fx_auto.rs`)

#### Scenario: A single clip is untouched
- **WHEN** the warp is edited on a clip without a pair
- **THEN** the rule does not run, and the project is byte for byte the same as before (the golden project of test 11 relies on this)
- **TEST** t248 `t248_lone_clip_is_untouched_by_the_rule` (`src/libs/kt-model/tests/fx_auto.rs`)

### Requirement: Warp map — two axes, profile from zero, reverse in normalization
The speed map SHALL distinguish the SIGNED position P = ∫rate (the media address) and the monotonic
CONSUMPTION A = ∫|rate| (the resampler cursor, trims); only A is inverted. The profile SHALL
start at zero: a key to the left of `source_in` (hidden by a trim) is clipped, not integrated.
The axis of the reverse mirror is the SPAN (min P, max P); the mirror lives in the normalization of
the profile, and the DSP knows nothing about reversal. The split at zero speed is enabled STRICTLY on a change of
sign: positive curves give a map bit for bit identical to the former one (a frozen oracle in the test).
`ease` on a rate curve is ignored: the map's formulas require a piecewise-linear profile.
Why: before clipping, every TrimStart and the right half of a Split read the material with an offset;
GOLDEN_* pins the bitwise identity of the old map.

#### Scenario: The profile always starts at zero
- **WHEN** the profile has a hidden key with a negative point
- **THEN** S(0) = 0 exactly, the integral on [0,1] is analytic, T = S⁻¹ is the inverse, and a profile without a negative point is not touched by a single bit
- **TEST** t269 (`src/libs/kt-model/src/warp.rs`)

#### Scenario: The curve of a mirrored clip does not play backwards
- **WHEN** a parameter curve of a reversed clip is converted into a profile
- **THEN** the normalization accounts for the reversal, and a key from the start of the event is applied at the start
- **TEST** t271 (`src/libs/kt-model/src/warp.rs`)

#### Scenario: The sign of speed is two axes
- **WHEN** rate passes through zero, sits on a plateau, and changes sign inside a segment
- **THEN** the position moves backwards, the consumption only grows, the split at zero is exact, the plateau holds the consumption, the span extrema are found inside the segments, the mirror axis is the span, the clamp is symmetric and zero is passed through; positive curves are bit-for-bit equal to the old map
- **TEST** t603a, t603b, t603c, t603d, t603e, t603f, t603g (`src/libs/kt-model/src/warp.rs`)

### Requirement: Mixing two states of one kind
The model SHALL be able to blend two states of ONE kind of effect by amount: the ends are given
byte for byte (without rebuilding), the amount is clamped to 0..1, numeric series are interpolated
with integer rounding, non-numeric values are taken from the nearer end, different kinds are not blended,
and the result stays within the spec for each kind.
Why: the strength axis in the effect picker depends on this — a click on a cell must yield exactly its
variant, otherwise the layout test would not see a discrepancy (capability `video-fx`).

#### Scenario: The ends are exact, the middle is in the middle
- **WHEN** two states of one kind are blended at t = 0, 1, beyond the bounds, and in the middle
- **THEN** the ends equal the originals byte for byte, the middle is interpolated, the non-numeric value comes from the nearer end, a foreign kind is rejected, and each kind stays within its spec
- **TEST** t550, t550b, t550c, t550d (`src/libs/kt-model/tests/fx_lerp.rs`)

### Requirement: Generator parameters live on the event
The values of a generator (the kind with values) and their curves SHALL live on the event; the media path
carries ONLY the kind (the exception is the "sort" of a variant, whose kind name has a value function).
The invariant "values exist if and only if the media is a generator, the kind matches the path,
an orphan curve is rejected" holds by construction (commands bring the path to canon and fit the values)
and by validation. The generator's curves are resolved BY THE SOURCE ITSELF at its own tick;
the compiled plan does not touch them. Editing a value goes through the retune strip
without rebuilding the renderer; the predicate "can be reconfigured" and the implementation do not diverge on a single
pair of states. The source address comes from the event; the list of sources is computed by one code
for the player, the export and kt-cli. Values are mirrored across the link group on one media.
Why: the title text was part of the media address, shared by all places — "change the header in the second issue"
had nowhere to be written; the owner's decision was "onto the event, like effects"
(sources and factory — capability `generators`).

#### Scenario: Values on the event, the path carries the kind
- **WHEN** values are cleaned out of a generator's path, and the variant sort and empty fields are serialized
- **THEN** the path carries only the kind (the sort stays in the path), empty fields are not written, and files without generators are byte-stable
- **TEST** t656 (`src/libs/kt-model/tests/genmedia.rs`)

#### Scenario: Values are checked against the media
- **WHEN** values exist on a file but are absent on a generator, the kind does not match the path, or a curve is orphaned
- **THEN** validation rejects each case explicitly
- **TEST** t657 (`src/libs/kt-model/tests/genmedia.rs`)

#### Scenario: Two titles of one kind — the order equals the reading

#### Scenario: A generator's curve moves the bytes deterministically

### Requirement: The segment shape lives on the key and has its own parameters
The interpolation shape SHALL belong to the KEY and describe the segment AFTER it, not the whole curve.
The set of shapes is closed, and each has its own parameters: linear (no parameters), third order (tension), step (no parameters), ease in and ease out (tension),
zigzag (number of periods, amplitude, profile — triangle/rectangle/sine), **segment formula**
(text; variables `s` — the fraction of the path 0..1, `a` and `b` — the values of the left and right key, `t` —
seconds from the left key; the same evaluator and the same closed set of operations as the source formula). The amplitude of a zigzag SHALL be set IN UNITS OF THE PARAMETER and clamped
by the target's passport, not as a fraction of the difference between keys: the most frequent zigzag is an oscillation around a
CONSTANT value, where the difference is zero. Each shape SHALL be a closed function of
`(fraction of the segment, ends, parameters)` without state; for the segment formula the ends are set by the
formula itself (as with a step, it may fail to coincide with the key), and an uncomputable text SHALL
be rejected at the command and on load, with its position and name, instead of giving a silent zero. The
default shape for new keys is a PROJECT field, not a machine setting; changing the default MUST
NOT touch keys that are already placed. The command "apply the shape to all segments" SHALL
exist for a curve and for an event, and lands as one history step. The value at the
last key is the extreme one; the shape of the last key does not apply.
Why: a single boolean for the whole curve expresses neither "this section as a step" nor a zigzag; a machine
setting would give "one file, two behaviours" (the lesson of Vegas), and an amplitude taken from the difference would
collapse the zigzag exactly where it is needed. R.67: the owner asked to "set something on separate areas" — the formula on a segment is exactly that area between two keys.

### Requirement: Curve — keys, segment shapes, formula layer and links combine and are removed separately
The value of a curve SHALL be computed in layers in a fixed order: the keys with segment shapes give `k`; on top — an optional LAYER-formula (text with the variables `k`, `t`, `src`), and on top of that — nothing; a link (`Link`) gives `src` and without a layer acts as before. Setting a

and SHALL be read as "a layer over empty keys" — that is, the same curve, only without keys.

be counted in seconds from the start of the curve's MATERIAL, identically in the render and in any
preview: a preview that counts `t` from the edge of the visible window would show a different
line from the one that sounds. Curves with formulas SHALL be resolved into numbers before the audio stream in the same
pass as links (the frame grid, byte-for-byte determinism); a project without formulas and links
MUST NOT pay anything.
The curves of OVERRIDES of a reel instance SHALL accept the same shapes and sources as the
